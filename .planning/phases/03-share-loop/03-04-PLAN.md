<objective>
**As a** raider reading the Raid tab, **I want to** see the awards card that is about to unfurl and
copy its link from right there **so that** sharing is one click at the point I decide to share.

This plan builds the in-app half of the share loop: the awards panel with its real inline preview,
the relocation of the share CTAs to where the content is read, and the landing-and-attribution
wiring that makes the loop measurable.

Purpose: SHARE-03's prominence half plus D-06, D-12, D-13 and D-16.
Output: an `AwardsPanel` on the Raid tab, a normalized header Share, the bottom bar removed, and
the `ref` landing funnel.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL query string to client state | `tab`, `fight`, `source`, `view` and `ref` are fully visitor-controlled and now drive tab selection, panel opening and an analytics property |
| client to PostHog | `share_action` and `share_landing` properties are assembled in the browser from those params |
| browser to the same-origin `/og` image | the panel embeds an image whose URL is built from the report code and fight id |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-14 | Tampering | `ref` param reaching a PostHog property | medium | mitigate | `parseShareRef` allowlists exactly three values; an unrecognised value fires no event and is stripped. Only the resolved value is ever passed into the capture (ASVS V5, RESEARCH Pitfall 5) |
| T-03-15 | Tampering | `tab` and `view` params driving the initial render | low | mitigate | `tab` is already narrowed to the three known modes; `view` is compared against a single literal to produce a boolean. Neither value is interpolated into markup or a URL that leaves the page |
