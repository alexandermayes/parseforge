# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase is narrower than most: it does not design new screens. It (1) wires a Google-owned,
self-rendering consent dialog (ParseForge does not control its copy or layout — D-04), (2) adds a
3-state theme toggle to the navbar (D-10), and (3) extends `app/globals.css`'s `@theme` block with
spacing/motion/elevation categories and a genuinely-designed light palette (D-09, D-11, D-12). The
contract below is scoped accordingly — most of it is "here is the token/behavior contract to build
against," not "here is new visual copy to write."

## Spacing Scale

Declared values (must be multiples of 4) — standard 8-point scale, no phase-specific override:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing |
| md | 16px | Default element spacing |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

**DSGN-01 deliverable:** `app/globals.css`'s `@theme inline` block currently has no explicit
`--spacing-*` token — it relies on Tailwind v4's implicit default base unit. Declare it explicitly
so the audit report can point to a real token, not an implicit default:

```css
@theme inline {
  --spacing: 0.25rem; /* 4px base unit — generates the whole spacing-N utility scale */
}
```

**Exceptions:** `.bar-primary` (10px / `0.625rem`), `.bar-sm` (6px / `0.375rem`), and `.bar-xs`
(4px) in `globals.css` are pre-existing progress-bar heights tuned for visual weight, not layout
spacing. `.bar-primary`/`.bar-sm` sit outside the 4px grid (10px, 6px). They are not part of D-11's
color/spacing/motion/elevation consolidation scope — flagged for awareness, not required to change
this phase.

## Motion & Elevation Tokens (DSGN-01 — new categories)

Not part of the base template but required by this phase's success criteria (spacing/motion/
elevation must resolve from `@theme` tokens). Extend the existing `@theme inline` block:

| Token | Value | Usage |
|-------|-------|-------|
| `--duration-fast` | 150ms | Micro-interactions — hover states, icon swaps (e.g. theme-toggle icon transition) |
| `--duration-base` | 200ms | Default transitions — migrates the existing hardcoded `200ms` in `.transition-interactive` (globals.css:353) |
| `--duration-slow` | 350ms | Modal/dialog enter-exit, larger surface transitions |
| `--ease-standard` | `cubic-bezier(0.4, 0, 0.2, 1)` | Default easing for all transitions |
| `--shadow-card` | `0 1px 3px oklch(0 0 0 / 12%), 0 1px 2px oklch(0 0 0 / 8%)` | Default card elevation — migrates `.surface-card`'s hardcoded shadow (globals.css:338) |
| `--shadow-elevated` | `0 4px 6px oklch(0 0 0 / 15%), 0 2px 4px oklch(0 0 0 / 10%)` | Modals, dropdowns, popovers (incl. the new theme-toggle dropdown-menu) — migrates `.surface-card-elevated` (globals.css:346) |

**Consolidation note:** `.surface-card`/`.surface-card-elevated` already hand-write these exact
shadow values inline. Point them at the new tokens (`box-shadow: var(--shadow-card)`) instead of
duplicating — this is the elevation category's "no known exceptions" bar per D-11.

## Color

Two live themes (dark = today's shipped palette; light = D-09's new deliverable), so values are
given as **semantic token pairs**, not single hex — never hardcode either theme's literal value in
a component.

| Role | Token (dark / light) | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` / `--foreground` — dark: `oklch(0.13 0.015 270)` bg, `oklch(0.985 0 0)` fg (unchanged, already shipped) — light: `oklch(0.98 0.006 270)` bg, `oklch(0.18 0.02 270)` fg (**new, D-09** — same 270 hue family as dark, not stock shadcn neutral gray) | Page background, body text |
| Secondary (30%) | `--card` / `--secondary` / `--muted` — dark: existing `surface-1`/`surface-2` scale — light: `oklch(1 0 0)` cards on a faint-tinted `oklch(0.94 0.008 270)` secondary/muted surface (contrast against the tinted background, not flat white-on-white) | Cards, nav/sidebar surfaces, table zebra rows |
| Accent (10%) | `--primary` (gold gradient `--gold-from`/`--gold-to`) — dark: `oklch(0.82 0.16 85)` → `oklch(0.72 0.14 60)` (unchanged) — light: darken/saturate for AA contrast on white, e.g. `oklch(0.55 0.14 85)` → `oklch(0.48 0.13 65)` (**new, D-09** — same hue, tuned lightness, same "Wowhead approach" principle as D-12) | Primary CTA buttons, active tab underline (`.tab-active-gold`), brand wordmark gradient (`.text-gradient-gold`), focus glow (`.glow-gold`) |
| Destructive | `--destructive` — dark: `oklch(0.704 0.191 22.216)` (unchanged) — light: darken for contrast, e.g. `oklch(0.5 0.22 25)` (**new, D-09**) | Destructive actions only (none introduced this phase) |

**Accent reserved for:** primary CTA buttons, the active-tab gold underline, the `ParseForge`
wordmark gradient, and focus/hover glow effects on already-accent elements. **Not** for large
surface fills, decorative backgrounds, or arbitrary highlight text.

**Contrast target:** WCAG AA (4.5:1) minimum for body text against its surface in both themes —
verify the light-palette proposed values above during implementation with a contrast checker
before treating them as final; they are a designed starting point per D-09, not a locked spec.

### Per-theme WoW class colors (D-12)

`CLASS_COLORS`/`ROLE_COLORS` in `lib/constants.ts` (11 + 4 raw hex values, consumed via inline
`style={{ color: ... }}` in 9+ component files) must become CSS custom properties with paired
light/dark values — e.g. `--class-warrior`, `--class-paladin`, ... `--role-tank`, defined once in
`:root` and once in `.dark`, consumed as `style={{ color: "var(--class-warrior)" }}`. **Do not**
convert these to Tailwind utility classes — they're not `className`-driven (see RESEARCH.md
Anti-Patterns).

Tuning principle for light backgrounds (the "Wowhead approach," D-12): preserve each class's
recognizable hue; reduce lightness / increase saturation for near-white or near-yellow classes so
they stay legible on a light surface. Concretely at risk: **Priest** (`#FFFFFF` → needs a
mid-gray/lavender-tinted variant, not white-on-white), **Rogue** (`#FFF569` → needs a deeper,
more-saturated yellow/gold), **Paladin** (`#F58CBA` → likely fine as-is or slightly deepened). Exact
final hex per class is an implementation-time tuning pass against a real contrast checker — this
section states the principle and the three highest-risk classes, not a fabricated final palette.

**Explicit exception, not audit debt:** `app/og/route.tsx`'s hardcoded hex mirror of `GRADE_COLORS`
exists because Satori (`next/og`) cannot resolve CSS custom properties — already documented in that
file's own comment. Preserve it; do not "fix" it into a token reference.

## Copywriting Contract

Most of this phase's user-facing surface is either owned by Google (the consent dialog) or is a
non-verbal icon control (the theme toggle), so the template's CTA/empty/error/destructive rows are
mostly N/A by design — filled honestly below rather than inventing copy that doesn't apply.

| Element | Copy |
|---------|------|
| Primary CTA | None introduced — theme toggle is icon-only, not a labeled CTA. Accessible name: `aria-label="Toggle theme"` on the trigger button; menu items read exactly `"Light"`, `"Dark"`, `"System"` (next-themes' own 3 values, sentence case, no icons-as-only-label) |
| Empty state heading/body | Not applicable — this phase adds no list/collection UI |
| Error state | Consent dialog copy itself is **Google-managed** (D-04: their standard GDPR format) — ParseForge does not author accept/reject button text. If the CMP script fails to load or is blocked (e.g. by CSP or an ad-blocker), there is no ParseForge-authored fallback banner — the visitor sees no prompt and PostHog stays fail-closed (cookieless, no replay) indefinitely per D-06's "pre-choice = not consented." This silent-fail-closed behavior is a `⚠ unresolved` planner decision below, not a locked answer |
| Destructive confirmation | None — no destructive actions introduced this phase. Consent "reject" is not styled/labeled as destructive (it's Google's own neutral-styled button, not a ParseForge delete-type action) |

**Instrumentation copy (Claude's Discretion, proposed for consistency — follows existing
`posthog.capture()` snake_case convention):**

| Event | Props | Fires when |
|-------|-------|------------|
| `consent_resolved` | `{ accepted: boolean, region: "eea_uk" }` | EEA/UK visitor accepts or rejects via the CMP dialog (from Pattern 3 in RESEARCH.md) |
| `theme_changed` | `{ theme: "light" \| "dark" \| "system" }` | Visitor picks a value from the 3-state toggle |

## UI Considerations

Probe run 2026-09-05 (`ui-consideration-probe.cjs`) over 3 elements: E1 theme toggle, E2 consent
dialog, E3 light-palette route surfaces. E2 element kinds confirmed with user: detected
`static-content` + added `interactive-control` (async load/error — the classifier's text-only cue
missed the CMP's async nature). Coverage: 20 applicable — 4 resolved (explicit), 1 resolved
(backstop), 2 unresolved (planner assumptions), 13 dismissed with reasons.

### Resolved — explicit (lift each as a truth)

| Element · Category | Acceptance criterion (verification: explicit) |
|---|---|
| E1 · loading | Initial paint shows the persisted theme with no flash-of-wrong-theme: `next-themes`' blocking inline script sets the `class` attribute on `<html>` before first paint (`attribute="class"`, `suppressHydrationWarning` on `<html>` per Pitfall 4) |
| E1 · populated | The open theme menu shows exactly three items — "Light", "Dark", "System" — with an active-item indicator, and the trigger icon tracks `resolvedTheme` (D-10) |
| E3 · populated | Every shipped route resolves color, spacing, motion, and elevation from Tailwind v4 `@theme` tokens in BOTH themes — the DSGN-01 token audit report demonstrates it |
| E3 · edge legibility | WoW class/role colors are per-theme CSS custom-property pairs (D-12); Priest, Rogue, and Paladin remain legible on the light surface (tuned variants, not raw `#FFFFFF`/`#FFF569`) |

### Resolved — backstop (structured marker for the planner lift)

- { statement: "During the CMP script load window the visitor sees the normal page — no half-rendered consent dialog shell and no layout shift attributable to the CMP", verification: backstop }

### Unresolved — ⚠ planner must treat as assumption

| Element · Category | Open decision |
|---|---|
| E2 · error | CMP script blocked (CSP violation or ad-blocker): `__tcfapi` never fires, the visitor silently never sees a consent prompt, and PostHog stays fail-closed (cookieless, no replay) indefinitely. Planner must explicitly decide whether silent fail-closed is accepted as final or a fallback is needed — not leave it as an implicit gap |
| E3 · zero-one-many | Full-route light-mode readability has NO automated visual-regression harness (node-env Vitest only — RESEARCH.md Open Question 3). Planner must schedule an explicit manual UAT sweep of every route in light mode; the token swap alone does not guarantee legibility |

### Dismissed (with reasons)

| Element · Category | Reason |
|---|---|
| E1 · empty, partial, zero-one-many | Static control — menu always has exactly 3 fixed items; no data-driven content |
| E1 · error | No async load/submit path; storage-unavailable falls back to next-themes' default (system) |
| E1 · overflow, long-text | Fixed icon trigger + three fixed one-word labels; nothing dynamic to overflow or truncate |
| E2 · overflow, long-text | Google owns the CMP dialog's layout, scroll behavior, and copy entirely (D-04) — not a ParseForge-authored surface |
| E3 · empty, error, partial | Pre-existing per-route states, unchanged this phase — only the tokens they resolve change; swept by the manual light-mode UAT above |
| E3 · loading | Theme-resolution loading is covered by E1 · loading; route-level loading states pre-exist unchanged |
| E3 · overflow | Token swap changes no box dimensions or layout — overflow behavior identical to shipped UI |
