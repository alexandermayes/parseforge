## Phase Goal

Every visitor is measured again - non-EEA/UK visitors are captured without depending on the Google
CMP, EEA/UK visitors keep the exact TCF gate, and the OPS-01 gate can never again pass on pre-deploy
data.

## User Story

**As a** developer whose five code-review fixes - including the one that stops `consent_resolved`
double-firing - sit on a branch while production runs the build that predates them, **I want to**
decide deliberately whether to ship them and, if I do, watch the same hardened gate run against the
new deploy, **so that** the EEA/UK test in the next plan is exercising the code I actually fixed
rather than the code I already know was wrong.

<objective>
Enable the WR-03 half of Gap A and the behaviour-unverified Truth 4, by making the production build
match the reviewed source - and pay the price the gate charges for doing so.

The production deployment every piece of live evidence in this phase rests on,
`dpl_HY5319wSDVw3M4ibBU42JrSTgw4e`, was built from commit `8693498`, which predates all five
code-review fix commits. The `consent_resolved` dedupe (`9da21c4`, WR-03) is therefore **not in
production**, and `02.1-VERIFICATION.md`'s human-verification item 2 explicitly asks for a CMP
re-confirmation to exercise exactly that dedupe. Testing it against today's production would prove
nothing about the fix.

So this plan offers the developer a decision, not a fait accompli: ship the five fixes, or do not.
Shipping is legitimate gap-closure work, and it is expensive - a new production deploy opens a new
60-minute window that Part 1 item 7 obliges this phase to measure for real, all three thresholds,
including another Vercel Web Analytics figure. That cost is stated in the checkpoint, before the
decision, not discovered after it.

Declining is a legitimate answer too. It is recorded verbatim, and 02.1-08 proceeds against the
current build with WR-03 recorded as unverifiable in production.
