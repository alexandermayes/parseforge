## Phase Goal

Every visitor is measured again - non-EEA/UK visitors are captured without depending on the Google
CMP, EEA/UK visitors keep the exact TCF gate, and the OPS-01 gate can never again pass on pre-deploy
data.

## User Story

**As a** developer who rewired the consent gate for everyone outside the EEA, **I want to** watch a
real EEA browser go through the CMP dialog and confirm nothing changed for those visitors, **so
that** MONY-01's promise - the TCF gate is exactly as it was - rests on something I have seen rather
than on a unit test of a pure function.

**What the consent-region path is supposed to do (D-05, unchanged from Phase 1).** `opt-in-full`
opts in and starts session replay; an explicit reject leaves the SDK in its `cookieless_mode:
"on_reject"` handling with no replay and no non-essential cookie; a `pending` state after
`CMP_TIMEOUT_MS = 3000` captures nothing at all. `deriveConsentGateOutcome` in `lib/consent.ts` is
the single pure mapper, and `applyOutcome` in `app/components/PostHogProvider.tsx` is the single
call site for `posthog.register`, `posthog.opt_in_capturing` and `posthog.startSessionRecording`.

**Why `consent_unavailable` may legitimately never appear.** D-07 records this as accepted: a
pending consent-region visitor is opted out by the SDK, so the very event that announces the failure
is dropped too. If the timeout path is exercised and no event arrives, that is the documented,
expected behaviour - not a new defect. Say so rather than treating it as a miss.

**The WR-03 dedupe, and what it needs.** Commit `9da21c4` adds a `capturedGatePathRef` guard so the
`__tcfapi` listener cannot fire `consent_resolved` / `consent_unavailable` twice when the CMP
re-emits a resolved TCF event for the same visit. It is observable only as a count: one opt-in
session should produce exactly one `consent_resolved`. **Whether it is in production depends
entirely on 02.1-07.** Read `02.1-07-SUMMARY.md` first: if the deploy was approved and ran, the
dedupe is live and testable; if the developer declined, production is still
`dpl_HY5319wSDVw3M4ibBU42JrSTgw4e` (commit `8693498`), which predates `9da21c4`, and any count
observed says nothing about the fix.

**Consent region set (`lib/geo.ts`).** EU-27 plus IS, LI, NO, GB and CH - 32 codes. Any of those
egress countries renders the Google CMP; the classifier fails closed on a missing or blank header.

**PostHog access.** `mcp__posthog__exec` with `execute-sql`. Run `switch-project 337485` first and
confirm the active project reads ParseForge - the connector's default is a different application.
Queries stay aggregate: event name, `consent_gate_path`, `$geoip_country_code`, `count()`. Bound
historical windows explicitly rather than relatively, and record which timezone the bounds were
interpreted in.

**No EEA egress exists in this environment.** This is not a tooling gap to route around - it has
been true for the whole phase, and it is why this plan is shaped as a human checkpoint rather than
an automated test. Vitest here runs in a `node` environment with no jsdom and no React Testing
Library, so there is no browser harness to substitute either (`COVERAGE.md` records that as a
deliberate opt-out, not an oversight).
