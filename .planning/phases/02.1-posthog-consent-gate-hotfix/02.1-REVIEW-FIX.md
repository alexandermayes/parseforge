## Fixed Issues

### CR-01: `/api/geo` response body is trusted without runtime validation — malformed response fails OPEN, not closed

**Files modified:** `app/components/PostHogProvider.tsx`
**Commit:** `90f5a46`
**Applied fix:** Replaced the compile-time-only `(body: { isConsentRegion: boolean })` cast
with a runtime `typeof` check on the parsed JSON. A malformed/differently-shaped body
(missing `isConsentRegion`, wrong type, or `null`) now resolves to `true` (consent region),
matching the existing `.catch` fail-closed path, instead of `!undefined === true` silently
opting the visitor in. Applied exactly as suggested in REVIEW.md.

### WR-01: No timeout on the `/api/geo` fetch — a hung request blocks capture indefinitely

**Files modified:** `app/components/PostHogProvider.tsx`
**Commit:** `0e03d9b`
**Applied fix:** Bound the geo fetch with `{ signal: AbortSignal.timeout(5000) }`. A timed-out
or hung request now rejects the fetch promise, which the pre-existing fail-closed `.catch`
handler already covers (`applyDecision(true)`), so `consentReady` can no longer be stuck
`false` forever behind a stalled request. Matches REVIEW.md's suggested fix.

### WR-02: `geo_header_missing` is logged for a missing/empty header but not for a blank (whitespace-only) one

**Files modified:** `app/api/geo/route.ts`, `app/api/geo/route.test.ts`
**Commit:** `7a7cf0c`
**Applied fix:** Compare the log-trigger condition against the trimmed header value
(`normalized = country?.trim()`) instead of the raw header, so a whitespace-only
`x-vercel-ip-country` header now logs `geo_header_missing` exactly once, matching how
`isConsentRegionCode` already classifies it (fail-closed to consent region). Added a new
test, "logs exactly one geo_header_missing line when the header is whitespace-only", which
also asserts the response still fails closed. Note: WR-04's return-type change was applied
in a separate commit (below) rather than bundled here, to keep each finding's diff atomic —
the two findings touch the same function signature line but are independent concerns.

### WR-03: TCF listener can fire the resolve callback more than once, re-triggering `posthog.capture("consent_resolved", …)`

**Files modified:** `app/components/PostHogProvider.tsx`
**Commit:** `9da21c4`
**Applied fix:** Added a `capturedGatePathRef` (`useRef<Set<string>>`) at component scope,
alongside the existing `appliedRef`. `applyOutcome` now only calls `posthog.capture(...)` for
a given `gatePath` the first time it's seen; `posthog.register`, `opt_in_capturing`, and
`startSessionRecording` still run on every call (they're idempotent, matching REVIEW.md's
note). Keyed by gate path rather than a single fired-once boolean, so a genuine decision
change (e.g. reject → later accept via a CMP re-confirmation flow) still gets counted as its
own event — only an identical repeat resolution is suppressed. **This finding is flagged
`requires human verification`** (see note below): the dedupe logic is a state-handling change
with no existing automated test harness for `PostHogProvider.tsx`'s TCF listener wiring (this
component has no `.test.tsx` file in the reviewed set), so correctness rests on `tsc --noEmit`
and the full existing suite staying green (162/162) plus manual reasoning, not an executed
test of the duplicate-event scenario itself.

### WR-04: `GET` handler is missing its explicit return-type annotation

**Files modified:** `app/api/geo/route.ts`
**Commit:** `9657535`
**Applied fix:** Added `: Promise<NextResponse>` to `export async function GET(request:
NextRequest)`, per `.claude/CLAUDE.md`'s Function Design convention. Applied as a separate
atomic commit from WR-02 even though both touch the same line, to keep each finding
independently revertable.
