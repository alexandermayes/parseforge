### Locked Decisions
- **D-01:** The consent-region decision is made server-side from Vercel's geo request headers (`x-vercel-ip-country`, ISO 3166-1 alpha-2), never from the client, never from `__tcfapi`. The client receives a single boolean, `isConsentRegion`, before `posthog.init` runs.
- **D-02:** Hard constraint on transport: delivering that boolean must not change the rendering mode of any route — `/` stays ISR (`revalidate = 3600`), `/guides/*`, `/tbc-audit`, `/privacy`, `/terms` stay static, and no route gains a per-request server render it did not have. Calling `headers()` in `app/layout.tsx` is not acceptable. Candidates: a Next `proxy.ts`/middleware that classifies at the edge, or a minimal `/api/geo` endpoint the client calls once before init. Must add at most one small request before the first capture and must not set any cookie for a consent-region visitor before they consent.
- **D-03:** The consent-region set is one exported constant in `lib/` (e.g. `lib/geo.ts`) with a unit test, defined as exactly the region set Google Privacy & Messaging's GDPR message is configured to target (EEA + UK, and Switzerland if Google includes it). Unknown or missing header ⇒ consent region (fail closed), and when on Vercel (`process.env.VERCEL` set) that case emits one `logEvent("geo_header_missing", …)`.
- **D-04:** Non-consent-region visitors: inside `posthog.init`'s `loaded` callback, call `ph.opt_in_capturing({ captureEventName: false })` (or equivalent that suppresses the default `$opt_in` event) and `ph.startSessionRecording()` immediately, with no `startConsentListener` and no `__tcfapi` involvement at all. The first `$pageview` must not be lost to ordering.
- **D-05:** Consent-region visitors: the existing TCF flow in `PostHogProvider.tsx` / `lib/consent.ts` is kept exactly as-is. This hotfix does not try to make pre-choice EEA visitors capture cookieless — deferred.
- **D-06:** The decision logic that maps `(isConsentRegion, ConsentAction)` → SDK calls is extracted into a pure, unit-tested function in `lib/consent.ts`, so the provider's `loaded` callback becomes a thin switch over its result. Tests live in `lib/consent.test.ts` (vitest, node env — no React Testing Library, this phase does not add one).

## Summary

The outage has one root mechanism and one contributing mechanism, both confirmed by reading the installed `posthog-js@1.360.0` source this session. Root mechanism (already diagnosed): `cookieless_mode: "on_reject"` makes `isOptedOut()` return `true` while consent is `PENDING`, and `capture()` silently drops every event while opted out — no queueing, no cookieless send. Non-EEA/UK visitors never get a `__tcfapi` callback (Google's CMP script never invokes the listener for them), so they stay `PENDING` forever. Contributing mechanism (newly found this session, not in the original diagnosis): `PostHogPageView`'s own `useEffect` calls `ph.capture("$pageview", …)` using the *module-singleton* `posthog` object obtained via `usePostHog()`; because React runs child effects before parent effects on mount, this fires **before** `PostHogProvider`'s own `useEffect` has called `posthog.init(...)`. Reading `capture()`'s guard directly in `dist/module.js` confirms it does nothing at all when `this.__loaded` (or `this.persistence`) isn't yet set — no queue, just a no-op. This means the very first `$pageview` on every page load, for every visitor regardless of consent region, is dropped for a second, independent reason from the consent bug. Both must be fixed for SC1's "first `$pageview` reaches PostHog within seconds of load" to actually hold.

The fix has four small, verified pieces: (1) a same-origin `/api/geo` Route Handler — not `proxy.ts`/middleware, not `headers()` in the layout — reads `x-vercel-ip-country` and returns `{ isConsentRegion: boolean }` with no cookie set, satisfying D-02's rendering-mode constraint because a Route Handler is its own route, isolated from the page tree that must stay ISR/static; (2) `posthog.init(...)` moves out of a `useEffect` and into module scope (the pattern PostHog's own Next.js docs show as the lightweight alternative), eliminating the child-before-parent effect race for `$pageview`; (3) `lib/consent.ts` gains a pure `deriveGateAction(isConsentRegion, tcfAction)` (or equivalent) that the provider's `loaded` callback switches over, extending the existing pure-function pattern rather than inlining new branches into the provider; (4) `docs/OPS-01-SHIP-GATE.md` gains the mandatory post-deploy HogQL live-traffic check specified in D-08, with the exact query given below.

**Primary recommendation:** Fetch geo classification from a dedicated `/api/geo` Route Handler (not middleware, not a layout `headers()` call); move `posthog.init()` to module scope to fix the effect-ordering bug alongside the consent bug; keep `lib/consent.ts`'s existing TCF logic untouched and add one new pure function for the geo/TCF merge.

### Pattern 1: Route Handler as the sole reader of geo headers (satisfies D-02)
**What:** A Route Handler at `app/api/geo/route.ts` is its own Next.js route, entirely separate from the page-route tree. Reading `request.headers` inside a Route Handler does not affect any page's PPR/ISR/static classification — only the specific route file that calls a dynamic API is affected by dynamic-rendering rules, and here that "route" is the API endpoint itself, not `/`.
**When to use:** Any time a per-visitor value (geo, user-agent, etc.) is needed by a client component on a page that must remain statically generated/ISR.
**Example:**
```ts
// Source: https://vercel.com/docs/headers/request-headers (x-vercel-ip-country),
// pattern confirmed against Next.js 15+ Route Handler default-uncached-GET change
// (https://nextjs.org/blog/next-15 — "GET functions are not cached by default")
// app/api/geo/route.ts
import { NextRequest, NextResponse } from "next/server";
import { isConsentRegionCode, CONSENT_REGIONS } from "@/lib/geo";
import { logEvent } from "@/lib/observability";

export async function GET(request: NextRequest) {
  const country = request.headers.get("x-vercel-ip-country");
  if (!country && process.env.VERCEL) {
    logEvent("geo_header_missing");
  }
  // Fail closed: unknown/missing header ⇒ consent region (D-03).
  const isConsentRegion = !country || isConsentRegionCode(country);
  return NextResponse.json(
    { isConsentRegion },
    { headers: { "Cache-Control": "private, no-store" } },
  );
}
```
Since Next.js 15 (carried into 16), Route Handler `GET` functions are **not cached by default** (`[CITED: https://nextjs.org/blog/next-15]` — "In Next.js 14, Route Handlers that used the GET HTTP method were cached by default unless they used a dynamic function... In Next.js 15, GET functions are not cached by default"), so this always executes per-request without needing `export const dynamic = "force-dynamic"` — though adding it is harmless, explicit documentation of intent and is recommended for clarity.

### Pattern 2: Module-scope `posthog.init()` (fixes the effect-ordering bug)
**What:** Call `posthog.init(...)` at module load time in the client component file, guarded by `typeof window !== "undefined"`, instead of inside `PostHogProvider`'s own `useEffect`.
**When to use:** Whenever a page-view capture (or any capture) must not race a provider's mount-time initialization — which, per the React effect-ordering rule below, it currently does.
**Example:**
```tsx
// Source: community-documented alternative to PostHog's official Next.js App
// Router guide; PostHog's docs primarily show the useEffect pattern but note
// this module-scope variant is the lightweight alternative used by their own
// instrumentation-client.ts guidance for Next.js 15.3+.
// [CITED: https://posthog.com/docs — Next.js installation docs, paraphrased;
//  exact wording not re-verified against a single canonical URL this session — ASSUMED for the precise phrasing]
"use client";
import posthog from "posthog-js";

if (typeof window !== "undefined" && POSTHOG_KEY) {
  posthog.init(POSTHOG_KEY, { /* ...same config... */ });
}

export default function PostHogProvider({ children }) {
  // no useEffect wrapping init() anymore
  return <PHProvider client={posthog}>{children}</PHProvider>;
}
```

### Anti-Patterns to Avoid
- **Calling `headers()`/`cookies()` in `app/layout.tsx` or any shared layout:** opts the *entire* subtree into dynamic rendering (`[CITED: Next.js docs via WebSearch — "Using [cookies/headers] in a layout or page will opt a route into dynamic rendering"]`), breaking `/`'s ISR guarantee. This is explicitly forbidden by D-02.
- **Assuming `capture()` queues events called before `init()`:** it does not. `capture(t,i,e){var r; if(this.__loaded&&this.persistence&&this.sessionPersistence&&this.$i){...}}` — reading the guard directly shows a bare early return with no `__request_queue` push in this path `[VERIFIED: node_modules/posthog-js/dist/module.js, the exact `capture(t,i,e){...}` method body, read this session]`. Any `capture()` call that races ahead of `init()` is silently dropped, not delayed.
- **Trusting `proxy.ts`/middleware to deliver a per-visitor boolean to a static page's client bundle without a cookie:** there is no documented Next.js mechanism for this; it either needs a cookie (forbidden pre-consent by D-02) or a client-side fetch.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| EEA/UK/CH region matching | A hand-maintained list scraped from memory of "EU countries" | `lib/geo.ts`'s `CONSENT_REGIONS` set, defined from the Google AdSense support doc's explicit EEA+UK+Switzerland list, unit-tested | A mismatch (over- or under-inclusive) is exactly today's bug in miniature — under-inclusive drops a real EEA visitor into non-consent-region opt-in (illegal); over-inclusive stops a legitimately non-EEA visitor from being measured (today's outage, in miniature) |
| Country → region membership lookup | Regex or substring matching on `x-vercel-ip-country` | A `Set<string>` of ISO 3166-1 alpha-2 codes, `.has(code)` | O(1), no ambiguity, trivially unit-testable per D-03 |
| Bounding a hung shell command (headless Chrome netlog) | A custom `setTimeout`/background-process-and-kill wrapper script | `perl -e 'alarm N; exec @ARGV'` (GNU `timeout`/`gtimeout` are both absent on this machine — confirmed this session) | `perl`'s `alarm` is already present (`/usr/bin/perl`, confirmed via `which perl`) and needs no new install; a hand-rolled bash background-and-kill wrapper is more failure-prone than a one-line `alarm` call |

**Key insight:** every "don't hand-roll" item above is a case where a plausible-looking manual list or heuristic silently diverges from an authoritative source (Google's own targeted-region list, ISO 3166-1) in a way that reproduces this exact phase's bug class — a region-matching bug is what caused the original 99.9% capture loss.

## Common Pitfalls

### Pitfall 1: Child-effect-before-parent-effect capture loss (newly found this session)
**What goes wrong:** `PostHogPageView` (mounted as a child inside `PostHogProvider`) calls `ph.capture("$pageview", …)` in its own `useEffect`. `PostHogProvider`'s `useEffect` calls `posthog.init(...)`. React runs effects bottom-up on mount (child before parent), so the page-view capture fires before `init()` has run — and since `capture()` no-ops entirely when `!this.__loaded`, that pageview is silently dropped on every single page load, independent of consent region.
**Why it happens:** The provider assumed `useEffect([])` ordering would guarantee `init()` runs "first" because it's declared in the outer component; React's effect-ordering rule is the opposite of that intuition.
**How to avoid:** Move `posthog.init()` to module scope (Pattern 2 above) so it runs synchronously the first time the module is evaluated — before any component's effects fire at all, not "in an effect that races other effects."
**Warning signs:** A netlog/network trace shows `/ingest/array/<token>/config.js` (the remote-config fetch, which happens as a side effect of `init()`) but no `/ingest/e/*` request timed near page load, even for a visitor who should be immediately opted in.

### Pitfall 2: Region-list drift from the CMP's actual target list
**What goes wrong:** `lib/geo.ts`'s constant is written from memory ("EU countries") instead of Google's actual configured target list, and drifts from what the CMP dialog is shown for.
**Why it happens:** "EEA" is not the same set as "EU" (adds Iceland, Liechtenstein, Norway); Switzerland was added to Google's policy only as of 2024-07-31 `[CITED: https://pandectes.io/blog/google-introduces-new-consent-requirements-for-switzerland/ — via WebSearch summary; not independently re-verified against Google's own dated policy-change note this session, so treat the exact date as ASSUMED]`; Gibraltar/Channel Islands/Isle of Man are not explicitly addressed by Google's support doc at all.
**How to avoid:** Base the constant strictly on Google's AdSense support doc's stated scope — "the European Economic Area (EEA), the UK, and Switzerland" `[CITED: https://support.google.com/adsense/answer/10961068]` — and treat anything the doc doesn't explicitly name (Gibraltar, Isle of Man, Channel Islands) as an open question requiring either a fail-closed default (already D-03's rule) or explicit developer sign-off on the code list, not a silent guess.
**Warning signs:** A country code with no CMP dialog shown, or a country with a dialog shown, that's on the wrong side of `CONSENT_REGIONS`.

### Pitfall 3: Vercel geo headers absent in local dev, no confirmed behavior on preview
**What goes wrong:** A developer tests `/api/geo` on `localhost` and sees `isConsentRegion: true` (fail-closed on missing header) and assumes that's broken, when it's actually the designed fallback.
**Why it happens:** `[CITED: https://vercel.com/kb/guide/geo-ip-headers-geolocation-vercel-functions]` — "When testing locally, the geolocation headers will not be set. You can only view geolocation information after making a deployment." The guide does not state whether preview deployments receive the same headers as production — this is an **absence**, not a confirmed "yes" `[ASSUMED — must be empirically confirmed at D-10's preview-deploy netlog step, not assumed true]`.
**How to avoid:** Treat "does the preview deployment receive `x-vercel-ip-country`" as an open question resolved empirically by D-10's own preview-deploy verification step (the netlog run against the preview IS the test), not by reading further docs.
**Warning signs:** The preview-deploy netlog shows `isConsentRegion: true` for a tester known to be outside the EEA/UK/CH — would indicate the preview doesn't receive real geo headers (unlikely, but not ruled out by documentation).

### Pitfall 4: `reset(true)` wiping state on the DENIED→opt-in transition (does not apply to this phase's path, but adjacent enough to flag)
**What goes wrong:** `opt_in_capturing()`'s source shows that when `cookieless_mode === "on_reject"` **and** `this.consent.isExplicitlyOptedOut()` (i.e., the visitor was in the `DENIED` state, not `PENDING`), the SDK calls `this.reset(!0)` before applying the opt-in, destroying the session manager and page-view manager `[VERIFIED: node_modules/posthog-js/dist/module.js, opt_in_capturing(t){...} method body, read this session]`.
**Why it happens:** This branch only fires for a visitor who was previously in the *explicit reject* state, not merely `PENDING`. The non-consent-region path in this phase calls `opt_in_capturing()` while consent is still `PENDING` (never having been set to `DENIED`), so this branch does **not** fire for D-04's flow.
**How to avoid:** Do not call `opt_out_capturing()` or otherwise force `DENIED` before the geo opt-in — confirm (as this phase's design already does) that the non-consent-region path opts in directly from the initial `PENDING` state.
**Warning signs:** Session-recording state or registered super properties unexpectedly reset immediately after opt-in — would indicate the visitor was somehow marked `DENIED` first.
