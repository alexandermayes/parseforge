**Reviewed:** 2026-09-14

## Summary

Reviewed the consent-gate hotfix: `lib/geo.ts` (server-side region classification),
`app/api/geo/route.ts` (the single header-reading surface), `lib/consent.ts` (pure TCF
decision + the new `deriveConsentGateOutcome` merge function), and `app/components/PostHogProvider.tsx`
(the single SDK executor). The pure-function core (`isConsentRegionCode`,
`deriveConsentAction`, `deriveConsentGateOutcome`) is solid — well-tested, fails closed on
blank/nullish/unknown input, and the gate-path/opt-in/replay/event mapping in
`deriveConsentGateOutcome` matches the documented D-05/D-06/D-07 decisions exactly, including the
correctly-tested invariant "never `startReplay: true` while `optIn: false`".

The gap is at the edge where the client trusts the network: `PostHogProvider.tsx` fetches
`/api/geo` and treats the parsed JSON body as validated data with no runtime check, which means a
malformed-but-valid-JSON response (a real, documented Vercel failure mode) **fails open** instead
of closed — directly contradicting the fail-closed invariant this hotfix exists to enforce. There
is also no timeout on that fetch (asymmetric with the TCF path's explicit `CMP_TIMEOUT_MS`
fail-safe), a header-logging gap between "missing" and "blank" country headers, and a
missing-dedupe gap in the TCF listener that can double-fire `consent_resolved`. `docs/OPS-01-SHIP-GATE.md`
was checked for leaked secrets and internal contradictions — none found; every bypass-secret
mention is explicitly redacted and the document is internally consistent.

## Critical Issues

### CR-01: `/api/geo` response body is trusted without runtime validation — malformed response fails OPEN, not closed

**File:** `app/components/PostHogProvider.tsx:95-106`
**Issue:** The geo fetch chain is:
```ts
fetch("/api/geo")
  .then((res) => res.json())
  .then((body: { isConsentRegion: boolean }) => {
    if (!mounted || appliedRef.current) return;
    applyDecision(body.isConsentRegion);
  })
  .catch(() => {
    // Fail closed...
    if (!mounted || appliedRef.current) return;
    applyDecision(true);
  });
```
`(body: { isConsentRegion: boolean })` is a compile-time-only assertion — nothing checks that the
parsed JSON actually has that shape at runtime. `applyDecision` then does `if (!isConsentRegion) { …
opt in … }` (`PostHogProvider.tsx:126`). If the response is valid JSON but lacks the field —
which happens for real, documented Vercel platform-level failures (e.g. a `FUNCTION_INVOCATION_FAILED`
/ timeout JSON error payload, or any intermediary that returns a differently-shaped JSON body) —
`body.isConsentRegion` is `undefined`, `!undefined` is `true`, and the code takes the
**non-consent-region branch and opts the visitor in immediately**, with no CMP involvement at all.
This is the exact opposite of the "fail closed" guarantee the code's own adjacent comment states
("a network or CSP failure must never opt a European visitor in") — that guarantee is only
implemented for the *promise-rejection* path (`.catch`), not for a resolved-but-malformed body,
which is the more likely of the two given how Vercel serverless failures are shaped. This directly
undermines D-03's fail-closed requirement and the GDPR/consent posture the whole hotfix is built on.
**Fix:**
```ts
fetch("/api/geo")
  .then((res) => res.json())
  .then((body: unknown) => {
    if (!mounted || appliedRef.current) return;
    const isConsentRegion =
      typeof (body as { isConsentRegion?: unknown } | null)?.isConsentRegion === "boolean"
        ? (body as { isConsentRegion: boolean }).isConsentRegion
        : true; // unexpected/malformed shape — fail closed, same as a network error
    applyDecision(isConsentRegion);
  })
  .catch(() => {
    if (!mounted || appliedRef.current) return;
    applyDecision(true);
  });
```

## Warnings

### WR-01: No timeout on the `/api/geo` fetch — a hung request blocks capture indefinitely

**File:** `app/components/PostHogProvider.tsx:95-106`
**Issue:** The TCF path has an explicit `CMP_TIMEOUT_MS` (3000ms) fail-safe so a blocked/absent CMP
can't leave a visitor `PENDING` forever — this is the exact bug this hotfix fixes. The geo fetch
that gates the *entire* decision (both the non-consent-region opt-in path and the start of the TCF
listener) has no analogous protection: a hung request (dropped connection, stalled edge function,
a service worker that never resolves the fetch) never hits `.then` or `.catch`, so
`applyDecision` is never called, `consentReady` never becomes `true`, and the visitor gets zero
capture — reproducing the class of bug this hotfix was written to eliminate, just via a different
trigger (a stalled request instead of a stuck consent state).
**Fix:** Bound the fetch with an explicit timeout, e.g.:
```ts
fetch("/api/geo", { signal: AbortSignal.timeout(5000) })
  .then((res) => res.json())
  .then(/* ... */)
  .catch(() => {
    // covers network failure AND the 5s timeout — fail closed either way
    if (!mounted || appliedRef.current) return;
    applyDecision(true);
  });
```

### WR-02: `geo_header_missing` is logged for a missing/empty header but not for a blank (whitespace-only) one

**File:** `app/api/geo/route.ts:14-20`
**Issue:**
```ts
const country = request.headers.get("x-vercel-ip-country");
if (!country && process.env.VERCEL) {
  logEvent("geo_header_missing", { route: "api-geo" });
}
```
`isConsentRegionCode` (and this file's own design intent per `lib/geo.ts`'s header comment and the
task brief: "fail-closed handling of a missing/blank/unknown country header … exactly one
`geo_header_missing` log") treats a blank/whitespace-only header identically to a missing one —
both resolve to `true` (consent region) after `.trim()`. But the logging condition here only
checks `!country`, which is `false` for a non-empty whitespace string like `" "`. So a blank
header is classified correctly (fail-closed) but silently — the observability signal this hotfix
relies on to measure how often the header comes back unusable under-counts the "blank" case.
Neither `route.test.ts` nor `geo.test.ts` (at the route level) covers this case, so the gap isn't
caught by the suite either.
**Fix:**
```ts
const country = request.headers.get("x-vercel-ip-country");
const normalized = country?.trim();
if (!normalized && process.env.VERCEL) {
  logEvent("geo_header_missing", { route: "api-geo" });
}
const isConsentRegion = isConsentRegionCode(country);
```
Add a corresponding test: a whitespace-only `x-vercel-ip-country` header logs `geo_header_missing`
exactly once.

### WR-03: TCF listener can fire the resolve callback more than once, re-triggering `posthog.capture("consent_resolved", …)`

**File:** `lib/consent.ts:154-171` (consumed at `app/components/PostHogProvider.tsx:138-146`)
**Issue:** `hasResolved` is only consulted by the *timeout* branch (`if (hasResolved) return;` inside
the `setTimeout` callback, `consent.ts:150`). The `__tcfapi` `addEventListener` callback has no such
guard — every time it receives a non-`"pending"` event, it calls `resolve(...)` unconditionally,
which in turn calls `onResolve`. Some CMPs (including Google Funding Choices, in "manage consent"
re-confirmation flows) can emit a second `useractioncomplete` event for the same visitor after the
first resolution. When that happens, `PostHogProvider`'s callback (`applyOutcome(deriveConsentGateOutcome(true,
action))`) runs again: `posthog.register` and `opt_in_capturing`/`startSessionRecording` are
effectively idempotent, but `posthog.capture(outcome.event, outcome.eventProps)` is not — a second
`consent_resolved` event is sent to PostHog for a single visitor's single consent decision,
inflating the metric the OPS-01 gate's HogQL query (`SELECT properties.consent_gate_path, count()
…`) uses to validate this fix. (The re-emit-after-timeout case is intentionally tested and correct;
this is specifically about a duplicate *non-timeout* resolution.)
**Fix:** Track whether a "real" (non-timeout) resolution has already fired, and skip the outbound
event (but still update `consentState`) on a repeat, e.g. in `PostHogProvider.tsx`:
```ts
const capturedGatePathRef = useRef<Set<string>>(new Set());
function applyOutcome(outcome: ReturnType<typeof deriveConsentGateOutcome>) {
  if (!outcome) return;
  posthog.register({ consent_gate_path: outcome.gatePath });
  if (outcome.optIn) posthog.opt_in_capturing({ captureEventName: false });
  if (outcome.startReplay) posthog.startSessionRecording();
  if (outcome.event && !capturedGatePathRef.current.has(outcome.gatePath)) {
    capturedGatePathRef.current.add(outcome.gatePath);
    posthog.capture(outcome.event, outcome.eventProps);
  }
}
```

### WR-04: `GET` handler is missing its explicit return-type annotation

**File:** `app/api/geo/route.ts:13`
**Issue:** `.claude/CLAUDE.md`'s Function Design convention states: "Always specify return type
explicitly. Async functions always return `Promise<T>`." `export async function GET(request:
NextRequest) {` has no return-type annotation. Every other exported async function reviewed in this
phase (`lib/consent.ts`'s functions) follows the convention; this route is the one exception.
**Fix:**
```ts
export async function GET(request: NextRequest): Promise<NextResponse> {
```

## Info

### IN-01: Geo fetch isn't aborted on unmount

**File:** `app/components/PostHogProvider.tsx:90-106`
**Issue:** The effect's cleanup sets `mounted = false`, which correctly prevents a late response
from mutating state after unmount, but the underlying `fetch("/api/geo")` request itself is never
aborted — it keeps running to completion (or failure) in the background. Low impact (the provider
mounts once for the app's lifetime in practice), but combined with WR-01's `AbortSignal.timeout`
fix, wiring the same controller into the cleanup function would also cancel the in-flight request
on unmount for free.
**Fix:** Reuse an `AbortController` created in the effect body; call `controller.abort()` in the
cleanup function alongside `mounted = false`.

### IN-02: `GET` handler has no JSDoc despite being this hotfix's single most security/privacy-sensitive export

**File:** `app/api/geo/route.ts:13`
**Issue:** The project convention calls for JSDoc blocks on exported (public-API) functions. This
file has rich prose above the `dynamic` export explaining the design rationale, but no JSDoc block
directly on the exported `GET` handler itself describing its contract (fail-closed on missing
header, no cookies, no caching) for a future reader who lands on the function signature first.
**Fix:** Add a JSDoc block immediately above `export async function GET`, e.g. summarizing:
"Returns `{ isConsentRegion: boolean }` for the requester's Vercel-detected country. Fails closed
(`true`) on a missing/blank/unrecognized header. Never caches, never sets a cookie."
