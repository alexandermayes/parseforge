## Warnings

### WR-01: `PostHogProvider.tsx`'s stateful orchestration (fetch, timeout, dedupe) has no test coverage of its own

**File:** `app/components/PostHogProvider.tsx:100-180`
**Issue:** Every automated test in this scope (`lib/consent.test.ts`, `lib/geo.test.ts`,
`app/api/geo/route.test.ts`) exercises a pure function. The component that actually wires
them together — the `/api/geo` fetch chain (including its `AbortSignal.timeout` race and
the runtime-shape validation added for CR-01), the `capturedGatePathRef` dedupe added for
WR-03, and the ordering guarantee in `applyOutcome` (register → opt-in → replay → capture)
that D-07 depends on — has no `PostHogProvider.test.tsx` and is not exercised by any test
in this repo. `02.1-REVIEW-FIX.md` itself flagged WR-03's fix as "requires human
verification" for exactly this reason ("no existing automated test harness for
`PostHogProvider.tsx`'s TCF listener wiring"), and that gap is still open on disk. A
regression in this file (e.g., a future edit that reorders `applyOutcome`'s calls, or
breaks the `mounted`/`appliedRef` guards under React's Strict-Mode double-invoke) would
not be caught by `npm test` today.
**Fix:** Add `app/components/PostHogProvider.test.tsx` using `@testing-library/react`
(or a hand-rolled render harness, matching this repo's existing conventions) with
`vi.stubGlobal("fetch", …)` to drive at least: (1) a malformed `/api/geo` body resolves
to the fail-closed opt-in-region path; (2) a fetch that never resolves is bailed out by
the 5s abort and still reaches `applyDecision(true)`; (3) two TCF `useractioncomplete`
events with the same decision produce exactly one `consent_resolved` capture call
(mocking `posthog.capture`/`opt_in_capturing`/`startSessionRecording` on the
`posthog-js` import).

### WR-02: The EEA/UK/CH consent-region code path (`tcf-accept`/`tcf-reject`/`tcf-timeout`) has never been exercised by a real browser

**File:** `app/components/PostHogProvider.tsx:160-174`, `lib/consent.ts:257-290`
**Issue:** This is the branch that decides whether an actual EEA/UK/Swiss visitor gets
opted into PostHog and session replay — the single most GDPR-sensitive code path this
hotfix touches. `docs/OPS-01-SHIP-GATE.md`'s own `### EEA/UK TCF observation (gap closure
02.1-08, 2026-09-15)` section records, in its own words, that this was **"Not
performed"**: no EEA/UK/CH egress was available to the automation, and the developer
declined the manual VPN session ("Stop asking for me to do things. Do it for me
please."). The same document's live-traffic queries (`### Re-deploy gate run`) show all
observed production traffic in every measured window routing through
`geo-non-consent-region` only — `tcf-accept`, `tcf-reject`, and `tcf-timeout` all read
count 0 in every window recorded. So today, confidence in this branch rests entirely on
(a) unit tests of the pure `deriveConsentAction`/`deriveConsentGateOutcome` functions and
(b) manual code reading — not on any observed real-world resolution of the TCF listener,
the `CMP_TIMEOUT_MS` fail-closed path, or the WR-03 dedupe fix against a real Google
Funding Choices dialog. This is a correct, honest gap already tracked in the project's
own docs — flagged here because it means the code in `app/components/PostHogProvider.tsx`
that actually calls `startConsentListener` and executes its outcome is, as of this
review, unverified in the one region it was built to protect.
**Fix:** Run the three sessions `docs/OPS-01-SHIP-GATE.md` already specifies (Session
A/B/C, EEA/UK/CH VPN egress, fresh private browser profile) before treating MONY-01 /
ROADMAP SC2 as behaviorally verified, not just logically correct. At minimum, run Session
B (full opt-in) once to confirm `tcf-accept` fires and session replay actually starts in
production.

## Info

### IN-01: The `consent_gate_path` dedupe can silently drop a `consent_resolved` capture whose event props differ from an earlier capture on the same gate path

**File:** `app/components/PostHogProvider.tsx:144-147`, `lib/consent.ts:274-281`
**Issue:** `capturedGatePathRef` dedupes purely by `outcome.gatePath` (a 4-member enum),
not by the full `ConsentGateOutcome`. `deriveConsentGateOutcome` maps two *different*
`ConsentAction`s to the same `gatePath`: `"opt-in-full"` and `"opt-in-non-eea"` both
produce `gatePath: "tcf-accept"`, but with different `eventProps.gdpr_applies` (`true`
vs. `false` — this is the documented "region-list-versus-CMP mismatch" backstop,
`consent.ts:232-239`). If a visitor's TCF listener ever emitted the mismatch signal
first (`opt-in-non-eea`, `gdpr_applies: false`) and *then* a later, genuinely-resolved
`opt-in-full` event (`gdpr_applies: true`) — both map to `tcf-accept` — the second
`posthog.capture("consent_resolved", { gdpr_applies: true, … })` call is silently
suppressed by the dedupe `Set`, even though its `eventProps` differ from the first and
would have corrected the earlier (anomalous) reading. Low impact: `optIn`/`startReplay`
still execute unconditionally on every call regardless of dedupe, so no privacy/opt-in
behavior is affected — this only affects the accuracy of the `gdpr_applies` value
recorded on the one `consent_resolved` event PostHog keeps for that gate path, for an
already-rare mismatch scenario.
**Fix:** If this distinction matters for the OPS-01 gate's HogQL queries, key the dedupe
`Set` by a composite of `gatePath` + the specific `ConsentAction` (or the serialized
`eventProps`) rather than `gatePath` alone, so a differently-propertied resolution on the
same gate path is still counted once. Given the narrowness of the scenario, this can
reasonably be left as documented behavior instead.
