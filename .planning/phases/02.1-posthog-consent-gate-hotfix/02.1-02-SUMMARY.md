## Decisions Made

- **Zero-events FAIL wording:** "zero `$pageview` events in the window is a FAIL, not a `no-data` row. A phase whose events cannot be observed fails this gate and may not be signed off as recorded-not-assumed. There is no override and no known-quiet-period allowance — if traffic is genuinely too low to reach 20 in an hour, widen the window and say so explicitly in the evidence rather than lowering the bar silently." Mirrored in the fourth recording rule: "A gate row about ingested events is passing only when it carries counted events — an absent count is a FAIL for that row, never a `no-data`."
- **Item 4's rewording removed exactly 2 lines** (the plan's additive-diff budget): the two lines reading "After deploy, confirm the event appears in the PostHog project's event definitions (needs real traffic). Evidence: the grep count pre-deploy, the event-definition screenshot/listing post-deploy." were replaced with new text explaining why a definition's presence proves past-not-current ingestion and pointing at item 7. The pre-deploy grep sentence immediately before it was left byte-for-byte unchanged.
- **`scripts/posthog-live-check.mjs` was not added**, per the discretion call already recorded in this phase's `COVERAGE.md`: a committed script would need a PostHog personal API key present on whatever machine runs the gate, adding a credential-handling surface to a hotfix whose whole point is to stay small. The live-traffic check instead ships as an exact, documented HogQL query run through the PostHog MCP (`switch-project 337485` first). A later phase that wants the script has this reasoning on record.
