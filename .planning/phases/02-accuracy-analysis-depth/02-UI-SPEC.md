# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase inherits Phase 1's fully-established token system and shadcn setup wholesale — no new
palette, no new spacing/typography scale, no shadcn re-init. It touches three existing surfaces
only: (1) a new **Timeline** sub-tab inside `AnalysisView.tsx`, (2) the **healer variant** of that
same player-analysis view (`DpsComparison.tsx` + `ComparisonSummary.tsx` suggestions), and (3) the
**Healer Breakdown** panel inside `RaidOverview.tsx`. Two elements are genuinely new to this
codebase's UI vocabulary — inline ability icons and multi-select filter chips — everything else is
prescribed by extending patterns already shipping in these exact files. Per D-01, the analyze page
itself is not redesigned (Phase 7); this spec is scoped to what D-01–D-08 actually touch.

## Color

Inherited from Phase 1's semantic token pairs (`01-UI-SPEC.md`) — this phase introduces **zero new
color tokens**. Every color below is an existing token used in a new place.

| Role | Token | Usage this phase |
|------|-------|-------------------|
| Dominant (60%) | `--background` / `--foreground` | Timeline tab body, unchanged page chrome |
| Secondary (30%) | `--card` / `--surface-1..3` | Timeline log wrapped in the same `Card` shell as other sub-tabs; row hover uses `hover:bg-surface-2` (matches `AnalyzeClient.tsx` tab-switcher hover) |
| Accent (10%) | `--primary` (gold) | **Not used anywhere in this phase's new UI.** No new accent surface is introduced — see reserved-for list below, unchanged from Phase 1 |
| Destructive | `--destructive` | Not introduced by this phase (no new destructive actions) |

**Accent reserved for (unchanged from Phase 1):** primary CTA buttons, the active-tab gold
underline, the wordmark gradient, and focus/hover glow on already-accent elements. **Filter chips'
selected state must NOT use gold** — chips are a multi-select control (unlike the single-select main
tab bar that legitimately owns `.tab-active-gold`), and several chips can be active simultaneously;
gold-per-chip would both violate the reserved-for list and read as multiple competing CTAs. Selected
chip state uses the neutral `bg-surface-3` treatment specified below instead.

### Status tokens used by this phase's new surfaces

| Token | Element | Meaning |
|-------|---------|---------|
| `--status-warn` | Idle-gap divider row (`bg-status-warn/10` background, `text-status-warn` label text) | A gap between casts longer than the relative idle threshold (D-03) — a caution, not a failure |
| `--status-bad` | Death-marker row (reuses `badge-bad` class verbatim from `RaidOverview.tsx`'s `DeathTimeline` "FIRST" badge) | The player died at this point in the log |
| `--status-good` / `--status-warn` / `--status-bad` | Healer overheal % and uptime % values (both in the player-page HPS tab and the raid overview `HealerPanel`) | Reuses the exact threshold bands already defined in `RaidOverview.tsx`'s private `overhealColor()` (≤20% good, ≤40% warn, else bad) and `activityColor()` (≥95% good, ≥80% warn, else bad) functions |

**Consolidation requirement:** `overhealColor()` and `activityColor()` currently live as
module-private functions inside `RaidOverview.tsx`. D-08 already requires one shared **data**
helper (`computeHealerMetrics`) so the two engines never disagree; this spec additionally requires
the **display** color-coding to come from one shared function so a healer's overheal-% badge is the
same color on the raid table and their own player page for the same fight. Extract both functions
into `lib/constants.ts` (alongside `percentileColor`/`percentileBg`) and import from both
`RaidOverview.tsx` and the player-page healer HPS card — do not re-implement the threshold bands a
third time.

## New Pattern: Inline Ability Icons

Genuinely new to this codebase — no component today renders a WCL/Wowhead ability icon as an
image; existing tabs (`CastEfficiency`, `AbilityBreakdown`) render ability names as text-only
`SpellLink`s whose Wowhead *hover* tooltip is the only place an icon has ever appeared. D-02
requires a persistent inline icon per timeline row, so this is new visual vocabulary, specified
here rather than left to improvisation:

- **Source:** WCL's `abilityIcon` field (already flowing through `analysis-engine.ts` as
  `icon`/`abilityIcon` on every ability-shaped object, e.g. `lib/analysis-engine.ts:322,367,426`) —
  a filename like `spell_holy_flashheal.jpg`. Render via Wowhead's static icon CDN:
  `https://wow.zamimg.com/images/wow/icons/medium/${icon}` (strip any trailing extension mismatch
  defensively; WCL's field already includes `.jpg`).
- **Element:** plain `<img>`, not `next/image` — the icon CDN is an external host with no
  `next.config.ts` `images.remotePatterns` entry today, and adding one is out of scope for a single
  24px decorative icon. `next.config.ts`'s CSP already allows `img-src https:`, so no CSP change is
  needed either.
- **Size:** 24px square (`w-6 h-6`), `rounded-[3px] border border-border/50` — a plain small border,
  not a WoW item-quality-tier border (that convention is reserved for gear/consumable icons
  elsewhere in the app if it exists; ability icons in a cast log are plain).
- **Loading/fallback:** `loading="lazy"`; on `onError`, swap to a fixed-size muted placeholder square
  (`bg-surface-2 rounded-[3px]`) rather than a broken-image glyph — the virtualised list means many
  icons mount/unmount rapidly during scroll, so a silent graceful fallback matters more than a retry.
- **Alt text:** the ability name (`alt={castRow.abilityName}`), so the row remains meaningful to
  screen readers even before/without the image.

## New Pattern: Cast Timeline (Timeline tab)

**Location:** new `TabsTrigger value="timeline"` / `TabsContent value="timeline"` pair in
`AnalysisView.tsx`, appended after the existing `casts` tab (D-01: "alongside DPS/HPS · Casts ·
Gear" — position it last so the existing tab order isn't visually reshuffled). Add `"timeline"` to
the `useUrlTabState("ptab", "dps", [...])` allow-list array (`AnalysisView.tsx:50-57`) — no other
change to that hook.

**Row anatomy (D-02 — vertical log, chronological, mobile-first):**

```
[ 0:42 ]  [icon]  Flash Heal              → Tirion
[ 0:44 ]  [icon]  Holy Light              → Tirion
──────── ⏸ Idle 3.8s ──────────────────────────────
[ 0:52 ]  [icon]  Renew                   → Self
```

| Column | Width | Style |
|--------|-------|-------|
| Timestamp | `w-14` fixed, right-aligned | `font-mono text-xs text-muted-foreground` — relative to fight start (`event.timestamp - fight.startTime`, RESEARCH.md Pitfall 3), format via the same `mm:ss` helper as `RaidOverview.tsx`'s `formatFightTime` (extract to a shared export rather than duplicating — both files need it) |
| Icon | `w-6 h-6` fixed | See "New Pattern: Inline Ability Icons" above |
| Ability name | flex-1, truncate | `.text-body-sm`, reuses `SpellLink` (same component `CastEfficiency.tsx` already uses) so Wowhead hover-tooltips keep working identically |
| Target | `w-24` fixed, truncate, right-aligned on desktop / stacks below on narrow mobile widths | `.text-caption text-muted-foreground`; "Self" when the target is the player themself, "—" when WCL reports no target |

**Idle-gap divider row (D-03):** a synthetic row (not a real cast) inserted between two consecutive
cast rows whose gap exceeds the relative threshold. Full-width, same 40px height as a cast row,
centered content: a thin `border-t border-dashed border-status-warn/40` line with a centered label
`⏸ Idle {N.N}s` in `.text-caption text-status-warn`. This is the row a raider scans for first when
answering "why was my parse low" — it must never be visually subtler than a normal cast row.

**Death marker row (D-03):** a synthetic row at the timestamp of the death event, full-width,
reusing the exact `badge-bad` treatment `RaidOverview.tsx`'s `DeathTimeline` already uses for its
"FIRST" badge — `text-[10px] font-medium px-1.5 py-0.5 rounded badge-bad` — but as a full-row band
(not just a small badge) so it reads as a hard stop in the log: `💀 Died` (Lucide `Skull` icon,
`size-3.5`, `text-status-bad`, not a literal emoji — matches the icon-library-only convention this
codebase otherwise follows).

**Per-ability filter chips (D-04):** a horizontal `flex flex-wrap gap-1.5` row above the log,
one chip per distinct ability that appears in the (already `JUNK_SPELL_IDS`-filtered) cast list,
plus a leading "All" chip. Each chip shows `{Ability Name} ({count})`. Chip style — raw `<button>`
with conditional classes, mirroring `AnalyzeClient.tsx`'s tab-switcher idiom exactly:

```
Unselected: text-muted-foreground hover:text-foreground hover:bg-surface-3 border border-transparent
Selected:   bg-surface-3 text-foreground border border-border
```

(Neutral selected state — no gold, per the Color section's reserved-for rule above.) Filtering
hides rows client-side only; nothing is re-fetched. "Nothing hidden by default" (D-04) — all chips
start selected/all abilities visible; clicking a chip toggles that one ability off, clicking "All"
resets to everything visible.

**Virtualisation:** fixed 40px row height (including divider/death rows) enables a simple
windowed-render approach — render only rows within a viewport-plus-buffer range behind a spacer
`div` sized to the full log's total height, per RESEARCH.md's "avoid a heavy dependency"
recommendation. This is an implementation detail, not a visual one — the contract is: **scrolling
must never show a blank flash**, and the filter-chip count in each chip label must reflect the
*unfiltered* total (so hiding an ability doesn't make its own count vanish before you can re-select
it).

**Truncation notice:** if the `/api/timeline` route hits its `MAX_PAGES` cap it must return
`truncated: true`, and the log then renders a final full-width 40px row in `.text-caption
text-status-warn` reading `Log truncated — showing first {N} casts`, so a capped log is never
mistaken for a complete one that shows no problems late in the fight.

**Loading state:** three stacked `Skeleton` blocks matching the row height (`h-10 w-full`), same
idiom as `AnalysisLoading()`'s existing skeletons — this is the state shown while the lazy fetch
(D-01: only on tab open) is in flight.

**Empty state (no casts recorded — e.g., a healer who only ever channeled, or a fight with zero
non-junk casts):** `<p className="text-sm text-muted-foreground">No casts recorded for this player
in this fight.</p>` — same tone/pattern as `CastEfficiency.tsx`'s existing `"No cast data
available."` empty line.

**Error state:** `<Alert variant="destructive"><AlertDescription>{error}</AlertDescription></Alert>`
— identical idiom to `player.error`/`raid.error`/`cla.error` in `AnalyzeClient.tsx`. Server-provided
message text (from the new `/api/timeline` route's error mapping) flows straight into this slot; no
new client-authored error copy is needed beyond a fallback: `"Couldn't load the cast timeline. Try
again."` if the route returns no message.

## Healer Metrics — Player Page (HPS tab)

`DpsComparison.tsx`'s existing card (headline metric + grade badge + percentile badge + You/
Previous/Median/Top bars) is **unchanged in structure** for healers — D-06 keeps the percentile and
the headline number, just grounds both in effective HPS (a data change, not a visual one; per
RESEARCH.md Assumption A5 the headline number likely already is effective HPS today).

**New, healer-only addition** — two comparison rows appended below the existing bars, only when
`role === "healer"`:

```
Overheal    You: 18%  ·  Top: 12%
Uptime      You: 91%  ·  Top: 97%
```

- Layout: same `flex justify-between text-sm` row shape as the existing bar labels (not a new bar —
  percentages aren't magnitude-comparable to HPS the way the DPS/median/top bars are).
- Label (`Overheal`, `Uptime`): `.text-body-sm text-muted-foreground`, left-aligned.
- Value: `You: {n}%` and `Top: {n}%` each individually colored via the shared
  `overhealColor()`/`activityColor()` helper (see Color section's consolidation requirement) —
  `font-mono text-sm`. This is the one place in the UI where a healer sees their number sitting
  directly next to the top-healer number for the exact same metric (D-06).
- Position: directly beneath the existing "Top" bar row, inside the same `CardContent`, no new
  `Card` wrapper.

**Healer suggestions (D-07):** render through the existing, unmodified `ComparisonSummary.tsx`
suggestion list (`priorityStyles`/`categoryLabels` badge + title + description card, already
generic). Two additions this phase must make to that component:

1. A new `categoryLabels` entry for whatever category key the healer rules use (e.g.
   `healing: "Healing"`) — the badge renders whatever label is missing as a raw uncapitalized key if
   this entry is skipped, which would read as a bug.
2. Copy content matching the established tone (second person, direct, one concrete number where
   possible) — proposed starting copy, thresholds/exact multipliers are Claude's Discretion per
   CONTEXT.md, wording should follow this shape:

| Rule (D-07) | Title | Description shape |
|---|---|---|
| Overheal well above top healers | `"High overheal"` | `"Your overheal is {N}% vs {top}% for top {spec}s. Avoid pre-casting or topping off full-health targets."` |
| Uptime well below top healers | `"Low healing uptime"` | `"Your healing uptime is {N}% vs {top}% for top {spec}s. Reduce idle time between casts and react to damage sooner."` |
| Effective-HPS gap with normal overheal/uptime | `"{Metric} gap despite efficient healing"` | `"Your effective HPS is {N}% below top {spec}s even though your overheal and uptime are in line. This points to gear or consumables, not technique."` |

DPS-shaped suggestions (`"Low active time (ABC)"`, CPM-gap copy) must not render for healers — the
existing `generateSuggestions()` already branches on `playerRole`; this phase's job is adding the
healer branch, not changing the rendering component.

## Healer Metrics — Raid Overview (`HealerPanel`)

`RaidOverview.tsx`'s `HealerPanel` (line ~237) already renders `hps`, `overhealPercent`, and
`activityPercent` per healer — its visual structure (colored player name, spec label, HPS bar,
overheal/uptime stat pills) is **unchanged**. What changes per D-08 is that the values feeding this
panel come from the new shared `computeHealerMetrics()` engine helper instead of the current
inline calculation, so the panel and the player-page HPS tab's new Overheal/Uptime rows (above) are
guaranteed to show the identical number for the identical healer+fight. No new visual element is
added to this panel this phase — this section exists to state explicitly that its current styling
(`overhealColor()`/`activityColor()` thresholds, `bg-status-good/60` HPS bar) is the reference
implementation the player-page rows above must visually match, not the other way around.
