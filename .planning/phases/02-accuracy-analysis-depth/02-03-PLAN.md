## Phase Goal

Raiders get verifiably correct analysis plus the per-fight depth competitors already offer.

<objective>
Turn the one-off, by-hand wago.tools verification that fixed PR #11's shifted id maps into a committed,
repeatable generator — so the class of bug that shipped wrong enchant and gem names to raiders cannot
recur silently.

This is the pipeline half of ACC-01: the script, the source-noted overrides layer, the three generated
era modules, and a regression test proving the generated data reproduces every ID-to-name pair the
existing suite pins. Plan 02-06 cuts `lib/cla-constants.ts` over to consume these modules and emits
`docs/GAME-DATA-AUDIT.md`.

Purpose: make "no hand-typed ID maps" a property the repository enforces rather than a habit the
author maintains (D-09, D-10, D-11).
Output: `scripts/regen-game-data.mjs` wired to `npm run regen-game-data`, three generated era modules,
one explicit overrides file, and a generated-data regression test.
</objective>

- Build discovery: `https://wago.tools/api/builds` lists builds per product.

- Tables: `SpellItemEnchantment`, `SpellName`, `SpellEffect`, `ItemSparse`, `GemProperties`.
- Enchant name join: `SpellEffect` rows with `Effect` of 53 or 54, whose `EffectMiscValue_0` is the

  leading `Enchant <slot> - ` prefix.
- Gem stat join: `ItemSparse.Gem_properties` -> `GemProperties.Enchant_ID` -> `SpellItemEnchantment`.

Create `scripts/regen-game-data.mjs` in the `scripts/token-audit.mjs` family: node shebang, a header
doc comment explaining the joins and the modes, `process.argv` mode parsing, explicit `process.exit`
codes. Add `"regen-game-data": "node scripts/regen-game-data.mjs"` to `package.json` scripts after
`record-fixtures`.

Modes, matching the family contract exactly: bare invocation is gate mode and exits 1 on any finding;
`--report` always exits 0 except on a fatal configuration error; `--markdown <path>` additionally
writes a markdown report, creating parent directories. Add two of its own:
`--build-<eraId>=<build>` pins one era to an explicit build instead of resolving it, and `--offline`
uses only already-cached CSVs and never reaches the network.

**Era descriptors.** Declare a single `ERAS` array as the script's one source of truth, each entry
carrying an `id`, a human `label`, a wago `product`, a `versionPrefix`, and the build currently pinned
in `lib/cla-constants.ts` recorded as `lastKnownBuild` for reference in the report:
`classic-tbc` / "Classic + TBC (Anniversary)" / `wow_anniversary` / `2.5.` / `2.5.6.69546`;
`wotlk` / "Wrath of the Lich King" / `wow_classic` / `3.4.` / `3.4.5.63697`;
`cata` / "Cataclysm" / `wow_classic` / `4.4.` / `4.4.2.60895`.
MoP is deliberately absent — do not add a fourth entry.

**Build resolution.** Fetch `https://wago.tools/api/builds` once and, for each era, select the newest
build whose version string starts with that era's `versionPrefix` within that era's `product`. Newest
means the highest numeric comparison of the dot-separated components, not a string sort — `2.5.6.9`
must not beat `2.5.6.69546`. If an era resolves no build, exit 2 with a message naming that era's id,
product and prefix. Never fall back to `lastKnownBuild` implicitly: falling back is only legal under
`--offline`, and the report must then say so per era. Two eras resolving to the same build string, or
any era resolving to a build whose prefix does not match its own, is a fatal error — that is exactly
the failure Pitfall 5 describes, where a previously-TBC-only id range suddenly resolves to a Cata
item name.

**CSV fetch and cache.** For each resolved build, download `SpellItemEnchantment`, `SpellName`,
`SpellEffect`, `ItemSparse` and `GemProperties` from `https://wago.tools/db2/<Table>/csv?build=<build>`
and cache each under `node_modules/.cache/regen-game-data/<build>/<Table>.csv`, which is already
outside version control. Reuse a cached file when present unless `--refresh` is passed. Parse the CSV
by header row so a column reorder upstream cannot shift fields — index every value by its header name,
never by position. A quoted field containing a comma must survive parsing; the enchant and item names
in these tables contain them.

**Row-count floors.** Declare a per-era, per-map minimum row count derived from the counts the current
hand-authored maps already carry for that era, and treat a generated map below its floor as a finding
that exits 1 **before any file is written**. A zero-row map is always fatal. This ordering is the whole
protection: an unreachable or truncated upstream must never be able to replace good data with less
data. Record every floor and its actual count in the report output.

**The three derivations.** Enchant names: from `SpellEffect`, keep rows whose `Effect` is 53 or 54,
read `EffectMiscValue_0` as the `SpellItemEnchantment` id, resolve the owning spell's name through
`SpellName` by spell id, and strip a leading `Enchant <slot> - ` prefix so the stored name matches the
style the existing map uses. Gem names: from `ItemSparse`, keep rows whose `Gem_properties` is
non-zero and take the item's display name. Gem stats: join `ItemSparse.Gem_properties` to
`GemProperties.Enchant_ID` to `SpellItemEnchantment`, read that enchantment's stat text, and classify
it into one `GemStatType` through a declared, table-driven text classifier — an unclassifiable stat
text yields `neutral` and is counted in the report rather than guessed at. Derive `badForRoles` from a
single `STAT_TYPE_BAD_FOR_ROLES` policy keyed on `GemStatType`, defined in the overrides file, not
per-id: today's data is already policy-consistent, with spell power bad for Physical, strength bad for
Caster and Healer, and defense bad for all three damage and healing roles.

**Emission.** Write one module per era at `lib/generated/game-data.<eraId>.ts`. Each begins with a
generated header stamping the era label, the wago product, the resolved build, the five source tables,
the generation date, and a line stating the file is written by `npm run regen-game-data` and must not
be hand-edited. Each exports era-suffixed maps so the eras stay distinct and a diff is attributable to
one client: an enchant-name map, a gem-name map and a gem-stat map, each named with the era's
upper-snake id suffix. Emit rows sorted by numeric id so a re-run diffs cleanly. Group them under the
same section-divider comment style `lib/cla-constants.ts` already uses.

**Cross-era collisions.** After generating all three eras, enumerate every id that appears in more
than one era with a differing value, and carry that list into the report. Do not resolve collisions in
the era modules — they stay separate by construction. Composition is 02-06's job and must preserve
today's behaviour: the current single map literal lists Classic, TBC, WotLK then Cata in order, so a
later entry already wins for a colliding id. Record that ordering explicitly in the report so 02-06
composes in the same direction rather than inferring it.

**The overrides layer.** D-11 calls for one explicit overrides file, and both the generator (a plain
`.mjs`) and the application (TypeScript) must read it, so it lands as a JSON data file with a thin typed
accessor beside it. `tsconfig.json` already sets `resolveJsonModule`, so the accessor can import the JSON
directly.

`lib/generated/game-data-overrides.json` is the single hand-authored data file — clearly the only place a
human writes game data, and the reason PR #11's bug is now impossible to hide, because a hand-sourced row
lives here and never inside a generated module. Give it three top-level keys to start:
`statTypeBadForRoles`, mapping each `GemStatType` to its `RaidRole` penalty list; `enchantNames`, and
`gemNames`, each an object keyed by numeric id whose value carries a `value` and a non-empty `source` note.
Seed it with the three override families D-11 names — WotLK and Cata food-buff friendly names, which client
data renders as one generic fed buff; the community-standard TBC food-buff id range; and engineering
tinkers — each with its own source note. Plan 02-06 adds a `consumables` key to this same file.

`lib/generated/game-data-overrides.ts` is the typed accessor: it imports the JSON and exports
`STAT_TYPE_BAD_FOR_ROLES` typed as `Record<GemStatType, RaidRole[]>`, `ENCHANT_NAME_OVERRIDES` and
`GEM_NAME_OVERRIDES` as `Map<number, string>` built from the JSON's value fields, and
`UNVERIFIED_OVERRIDE_IDS` as a `Set<number>` of every id present in the JSON's override sections — the
registry of every value that came from a human rather than a client dump. Add no data of its own; it is a
projection, so there is exactly one place to edit.

Add the same fatal startup check `token-audit.mjs` uses for its allowlist: the generator refuses to run, in
any mode, when any override entry in the JSON has an empty or missing `source` note. An unexplained
exception is precisely the silent omission this gate exists to prevent.
